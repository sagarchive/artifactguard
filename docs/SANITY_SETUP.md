# Sanity setup

Takes about 30 minutes. You need a Sanity account and Node 22.

## 1. Project and Studio

1. Create a project at [sanity.io/manage](https://www.sanity.io/manage) and copy its project ID.
2. Install and deploy the schema. Context requires a deployed schema and Studio for dataset endpoints.

```bash
cd studio
cp .env.example .env        # set SANITY_STUDIO_PROJECT_ID
npm install
npx sanity login
npx sanity deploy --url <your-studio-name>   # builds, deploys the Studio and the schema
```

3. Import the seed data. It has 363 documents and 848 native references. To refresh an existing dataset, add `--replace`, then delete any ids that no longer appear in the seed.

```bash
npx sanity dataset import ../data/sanity-seed.ndjson --dataset production
```

Open the Studio to confirm the documents are there. `npm run lint:seed` in the repo root checks the seed offline.

## 2. Knowledge Base

1. In Manage, open the organization, then **Labs**, and enable **Context**.
2. Open **Context**, then **New knowledge base**. Give it a title and a purpose line.
3. **Add source → Files**, upload everything in `knowledge-base/`, then **Build entries**.
4. Read **Entries** and **Issues**.

The same steps work from the command line. The CLI installed with the Studio may predate the `context` command, so use the latest:

```bash
npx @sanity/cli@latest context list --organization <org-id>
npx @sanity/cli@latest context imports create <kb-id> --file knowledge-base/01-oddy-test-scope.md   # one per file
npx @sanity/cli@latest context build <kb-id> --watch
```

Sanity writes the entries, and its writer adds wording the source files do not contain, such as a claim that two formulations are the same product. Three things keep the entries faithful:

- A **standing instruction** (Instructions tab, or `client.context.instructions.create`) that tells the builder to use only statements in the files, scoped to all of the sources. An instruction is tied to source ids, so replacing a file gives it a new id. Recreate the instruction after replacing any file.
- Resolving or dismissing **Issues**. Sanity flags contradictions between entries and sources. Dismiss a conflict that is a genuine disagreement between sources, such as the Terostat formulation name, instead of choosing a side.
- `npm run verify:kb`, which lists sentences in the built entries whose words are mostly absent from `knowledge-base/`. It needs the endpoint and token in `.env`.

Entry paths are generated by Sanity and can change when it rebuilds. Entries are found by search, using the topic queries in `TOPICS` (`src/agent/guidance.mjs`). `npm run check:deployed` fails if the Knowledge Base returns no entries.

## 3. Two Context endpoints

Dataset and Knowledge Base sources need separate endpoints. A mixed endpoint serves GROQ tools only.

| Endpoint | Source | Notes |
|---|---|---|
| `artifactguard-graph` | Dataset `production` | Filter: `_type in ["product","productRevision","oddyTest","testProtocol","emissionObservation","compound","interaction","artifactMaterial","evidenceClaim","source"]` |
| `artifactguard-knowledge` | The Knowledge Base only | |

The endpoint name cannot be changed later. Its URL has the form `https://api.sanity.io/v1/context/organizations/<org-id>/mcp/<name>`.

## 4. Token

In Manage, open the organization's **API → Tokens** and add a token with the **Context** permission set to **Viewer**. Under project access, add the project with the Viewer role. The token is shown once. It stays on the server and never goes in the browser or the repo.

## 5. Configure and verify

```bash
cp .env.example .env
# set SANITY_GROQ_MCP_URL, SANITY_KB_MCP_URL, SANITY_ORGANIZATION_TOKEN
ARTIFACTGUARD_MODE=live npm start
curl -s localhost:3000/api/context-status
```

The response must list `groq_query` under `groqTools` and `knowledge_base_search` and `knowledge_base_read` under `kbTools`. Then open the app and load the flagship case. The Knowledge Base box should say "Live Sanity Knowledge Base".
